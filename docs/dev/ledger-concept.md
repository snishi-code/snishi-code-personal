# simple-ledger — 会計コンセプト

個人カテゴリの家計簿アプリ `simple-ledger` の会計モデル。実装は
`apps/simple-ledger/src/domain/`。

## なぜ Spreadsheet ではなく PWA か

旧版は GAS + Google Spreadsheet で、入力のたびに Google サーバーと通信していた。
これはサイト憲法（**外部送信ゼロ・例外なし**）と両立しない。本アプリは概念だけを
引き継ぎ、次の前提で作り直した。

- **外部送信ゼロ**: アプリ内に `fetch` 等の送信系を一切持たない。
- **ローカルファースト**: 実行時の正本は端末内 IndexedDB。
- **オフライン動作**: Service Worker で app shell をキャッシュし、ネット無しで動く。
- **公式交換形式は JSON**: 端末間共有・バックアップは JSON export/import で行い、
  同期はアプリ外手段（Obsidian Sync など）に委ねる。アプリは同期・送信を実装しない。

> 旧 GAS コードは参照しない・移植しない。命名（`INPUT` / `PL` / `BS` / `CF` /
> `INVENTORY`）も使わない。すべて会計の標準語彙へ翻訳した。

## 中核モデル

- **`Account`（勘定科目）**: `id` / `name` / `type` / `role` / `startDate?` / `endDate?` /
  `archived` / `movable?`。各科目も時間軸上の線分であり、開始日・終了日の両端を含む。
  `startDate` 未設定時は `createdAt` の日付部分を開始点とみなし、終了点なしは未来へ続く。
  `type` は `asset` / `liability` / `equity` / `revenue` / `expense`（会計分類）。
  `role` は UI 用の役割で、日常入力（収入/支出/振替）の候補制御に使う。正本は
  [`apps/simple-ledger/src/domain/accountRoles.ts`](../../apps/simple-ledger/src/domain/accountRoles.ts)。
  `role` は `type` と整合する（`roleAllowsType`）。
  - `daily-asset`（現金・預金）/ `investment-asset`（投資）/
    `continuing-cost-asset`（継続コスト台帳＝集約口座・内部）… `type=asset`
  - `payment-liability`（クレジットカード等）/ `other-liability`（ローン等）… `type=liability`
  - `income-category`（`revenue`）/ `expense-category`（`expense`）/ `equity`（`equity`）
  - `system-adjustment`（残高調整費/収入。`expense|revenue`。自動生成・通常入力に出さない）
  - 内部集約ロール（`continuing-cost-asset`）は勘定科目管理・通常入力候補に
    出さない（`isInternalRole`）。BS / 資産内訳には 1 行で表示する。
  - **`movable`（「自由に動かせる」）は現預金（`daily-asset`）のみのフラグ・既定 ON**。
    Suica・チャージ残高など「支払いには使えるが自由に引き出せない」ものだけ OFF にする
    （例外側に印）。保存されるのは `false` だけ（ON は `undefined` へ正規化・保存境界と
    import 検証の両方）。使い道は資金繰りの原資（下記）だけで、BS / 資産の内訳は従来どおり
    全資産を出す。
- **`JournalEntry`（仕訳）**: `date` / `description` / `lines[]` / `kind` / `memo`。
  `lines` は「1 借方・1 貸方・同額」の 2 行のみ（型は複数行を許し将来拡張可能）。
  `kind` は `normal` / `opening`（初期残高）。
- **`JournalLine`**: `accountId` / `side`（`debit`/`credit`）/ `amount`（正の整数・1/100 単位（minor・v11〜））。

### 複式の符号ルール（`domain/accounting.ts`）

- `asset` / `expense` … 借方が正（残高 = Σ借方 − Σ貸方）
- `liability` / `equity` / `revenue` … 貸方が正（残高 = Σ貸方 − Σ借方）

例（変動費 1000 円を現金で支払う）:

```
借方 変動費(expense) 1000 / 貸方 現金(asset) 1000
```

→ 変動費 +1000（費用増）、現金 −1000（資産減）。

## 3 つの登録パターン（作者の整理・これが正典）

**① 通常**: ユーザーが「日付・項目名・金額・借方→貸方」を登録 → その日付の仕訳になり
**データとして残る**（残さないとどこからも再生できないから保存する）。

**② 継続コスト資産の購入**: 購入の仕訳を登録（例:
`ドラム式洗濯機（ローン）→ 継続コスト台帳` 240,000）。**これは残る**。同時に継続コスト資産に
「ドラム式洗濯機」が生まれる。終了日が未登録のうちは費用として割り振られない（資産として
持っているだけ）。終了日を登録すると開始日〜終了日で割り算され、未来の日付ぶんまで仕訳が
生まれる。**データとして保存されるのは 項目名・金額・開始日・終了日・費用の行き先だけ**で、
費用の行は計算式に則って展開される。

**③ 定期購入（ルール）**: 仕訳を生むルール。登録すると未来にかけて仕訳が生まれる。継続コスト
資産になるもの（N ヶ月ごとの支払い）なら、その資産と、それが費用へ割り振られる仕訳も裏で
計算されて生まれる。**データに保存されるのはルールと、起票済みの仕訳・item だけ**。

## PL / BS の導出

PL も BS も **保存しない**。`Account` と `JournalEntry` から毎回計算する（単一の正本）。

- **PL**: `revenue` と `expense` の残高から。`netIncome = totalRevenue − totalExpense`。
  期間 `[from, to]`（両端含む）で絞り込める。
- **BS**: `asset` / `liability` / `equity` の残高から。未締めのため、当期純損益
  （`revenue − expense`）を `retainedEarnings` として純資産に算入し、貸借を一致させる。
  - `純資産(netAssets) = 資産 − 負債 = equity 科目合計 + 当期純損益`
  - `balanced` フラグで貸借一致を検証（仕訳が常に balanced なら true）。

### フローとストックは同じレポート基準で切る

Dashboard / 各内訳ページは共有の `ReportPeriod` と `reportBasis(period, today)` から、フロー期間と
BS 基準日を同時に得る。PL だけ期間末、BS だけ今日、という片側の境界ずれを作らない。
ヘッダーは**日付を 1 つ選んでその断面を見る**（既定 = 起動時の当日）。

画面集計は `reportEntriesForAsOf(ledger, asOf)` で選択日まで必要な「計算で生まれる仕訳」を展開する。
「毎月のもの」も同じ `asOf` を表示基準にし、その日までに開始した定期ルール・継続コスト資産だけを
表示する。終了判定・今月の計上額は同じ日付で切る一方、回収・item の金額と期間は常に現在わかっている
全実仕訳を導出パラメータにする。したがって後日の回収はすべての月割り対象月へ遡及し、どの断面でも同じ月額になる。
ただし、ヘッダーは表示のタイムマシンであって書込日ではない。catch-up と新規作成・編集・アーカイブの
既定日は実際の今日を使う。

年・全期間の俯瞰は、ヘッダーとは独立した「年間・全体」画面で行う。年間は1〜12月、全体は
データのある年を列にし、PL集約・費目別・期末BSを同じ表に出す。現在・未来も同じ地図として扱い、
各列は常に月末・年末までの実仕訳と仮想投影を数値で示す。表示範囲の最大基準日まで
`reportEntriesForAsOf` を1回だけ実行し、`periodMatrix` が展開済み仕訳を日付順に単一走査して、
フローの列バケットとストックの期末スナップショットを同時に作る。終了日を持つ継続コスト資産と
定期ルールは、まだ実仕訳がない未来年もその線分が存在する年として列・年送り候補に含める。

### どこまで展開するか（計算量）

**表示している日付まで**。起動時は当日、資金繰りは少し未来まで、ユーザーが日付を変えたらそこまで。
上限は 2 つ: ルールの起票列挙は 1,200 ヶ月（`CATCH_UP_HARD_CAP_MONTHS`）、継続コスト資産の展開は
`2100-12-31`（`CONTINUOUS_COST_HARD_CAP`）で頭打ちになる。継続コスト資産の費用の行は**終了日で
止まる**ので、表示日を遠くしても件数は増えない。表示日ピッカーには `max=2100-12-31` を付け、
エンジンが展開できない範囲をそもそも選べなくする（入力欄の日付には `max` を付けない）。

## 初期残高

開始時点の資産・負債は **仕訳として** 登録する（`kind = 'opening'`）。UI では「初期残高」と
見せるが、集計上は通常の仕訳と同じに扱う。これにより BS の導出ロジックを 1 本に保てる。

例: 現金 100,000 円 → `借方 現金 100000 / 貸方 初期残高(equity) 100000`（kind=opening）。

- **登録導線はホームの日常入力ではなく「補正・勘定科目」画面**(`createOpening` / `updateOpening` /
  `deleteOpening`)。新規 BS 科目の作成 + 初期残高付与、既存科目への付与の両方に対応し、あとから
  編集・削除できる。資産: `借方 科目 / 貸方 初期残高`、負債: `借方 初期残高 / 貸方 科目`。

## 日常入力（収入/支出/振替）→ 仕訳への変換

ユーザーには借方/貸方を意識させず、意味のあるフィールドで 2 科目を選ばせる。内部では
必ず複式へ変換する（対応は `src/ui/entryModes.ts`、入力方法は `JournalEntry.metadata.inputMode`）。

| 入力         | フィールド（debit / credit）     | 候補ロール                                                                        |
| ------------ | -------------------------------- | --------------------------------------------------------------------------------- |
| 収入         | 入金先(debit) / カテゴリ(credit) | daily-asset / income-category                                                     |
| 支出         | 使い道(debit) / 支払元(credit)   | expense-category / daily-asset・payment-liability                                 |
| 振替         | 振替先(debit) / 振替元(credit)   | daily-asset・payment/other-liability（資金移動・返済・借入。`transferFlowValid`） |
| 詳細(manual) | 借方 / 貸方                      | 継続コスト台帳（`continuing-cost-asset`）以外すべて                               |

例（支出）: カテゴリ=変動費・支払元=現金・1000 →
`借方 変動費(expense) 1000 / 貸方 現金(asset) 1000`（metadata.inputMode='expense'）。

## 取消/返金（逆仕訳）

実取引のキャンセル・返金は、元仕訳を**削除せず**、借方/貸方を入れ替えた逆仕訳を作る
（`reversalInput`）。金額は既定で元と同額、編集可能（部分返金）。`metadata` に
`inputMode='reversal'` と `reversalOfEntryId`（元仕訳 ID）を残す。入力ミス直後の訂正は
編集/削除でよいが、実取引の取消は逆仕訳を推奨する。

## 継続コスト資産（4 項目モデル）

サブスクの年払い・前払い・耐久財など「買った時点で使い切らないもの」を、**項目名・金額・
開始日・終了日（任意）**の 4 項目で持つ償却対象として扱う（`MonthlyCostItem`。ほかに
`expenseAccountId`=費用の行き先を持つ）。実装は `src/domain/monthlyCost.ts` /
`src/domain/continuousCost.ts` / `src/data/repository.ts`。

- **購入の仕訳は保存される**: `借方 継続コスト台帳 / 貸方 支払い元`（資金・カード・ローン・
  初期残高）。日付 = `item.startDate`（日レベルで完全一致・不変条件）。印は
  `metadata.monthlyCostId` のみ。台帳は単一の集約口座（well-known id `continuing-cost-ledger`
  『継続コスト台帳』）で、品目ごとに勘定科目を作らない（品目名は `MonthlyCostItem.name`）。
- **費用の行は計算で生まれる**: 統一原則は「**支払いが買った期間を同日刻みで n 等分し、各刻みの
  終端の日に費用化する。残高 0 になる日 = 期間の終わり = 次の支払い日**」。終了日があるとき、
  刻みごとに `借方 費用の行き先 / 貸方 継続コスト台帳` が展開される（正本は
  `allocationSchedule`（`src/domain/monthlyCost.ts`）。導出仕訳への変換だけが
  `continuousCostEntriesForItem`）。この行はデータに残らない。
  - **k 番目の刻み日 = 購入日の k か月後の同日**（月末クランプ・起点は常に元の購入日なので
    1/31 購入なら 2/28・3/31 と日を保つ）。**n = 刻み日 ≤ 終了日を満たす最大の k**（同日通過の
    回数）。端数は `monthlyAmounts` で先頭の刻みから 1 円ずつ・合計は必ず金額に一致する
    （**月割り**であって日割りにしない）。
  - **購入日当日の費用は常に 0**。月払いの費用は翌月の同日に立ち、PL が 1 刻み遅れる。これは
    意図した挙動（「今日買ってもまだ消費していない」）で、購入より前に費用の行が立って台帳が
    マイナスになることも構造的に起きない。
  - **同日通過が 0 回**（終了日 < 購入日の 1 か月後）なら、終了日に全額 1 本を費用にする。
- **終了日が未設定なら何も生まれない**: 費用 0・残存価値 = 金額全額・BS に全額が乗り続ける
  （まだ費用にしていないのだから正しい）。終了日を入れて初めて割り算される。
- **終了日は自由に動かせる（過去も変わる）**: 費用の行は保存されないので、終了日を書き換えた
  瞬間に全期間が新しい刻みで再計算される。遡及処理は存在しない。3 年前に 24 万円で買ったものを
  過去日そのままで登録してもよい（持ち込み登録。貸方 = 初期残高・kind='opening'）。
  過去の収支が動いても今日の総資産はずれない。
- **開始日は購入の仕訳に紐づく**: item のシートでは読み取り専用で、変えるときは購入の仕訳の
  日付を変える（双方向ミラー: item の金額を変えると購入の仕訳へ、購入の仕訳の日付・金額を
  変えると item へ、同一トランザクションで書き戻す）。購入の仕訳は単独削除不可
  （item 削除で cascade）。
- **残存価値** = 金額 −（表示日までに費用になった額）−（回収の振替の額）。台帳口座の残高が
  そのまま全項目の残存価値の合計になる。

### 数字を決める規則（同日刻み）

- **8/15 に 240 万円・120 ヶ月（終了日 = 10 年後の 8/15）**: 刻み日は 9/15・10/15… と毎月 15 日で
  120 回。9/15 から毎月 2 万円ずつ費用になり、10 年後の 8/15 に残高 0 になる（= 期間の終わり）。
- **4/10 に 10 万円で購入 → 10/20 にアーカイブして 5 万円回収**: 同日通過は 5/10・6/10・7/10・
  8/10・9/10・10/10 の 6 回。割り振る総額（10 万 − 5 万 = 5 万）を 6 回に配る。10/10〜10/20 の
  端数期間ぶんの刻みは作らない（日割りしない）。
- **8/15 に購入 → 8/20 に終了**: 同日通過が 0 回なので、8/20 に全額 1 本を費用にする。

### アーカイブと振替

- **アーカイブ = 終了日をその日に設定すること**。終了日を過ぎた item は一覧から消える（導出
  `isArchived`。専用フラグや status は持たない）。終了まで 1 ヶ月以内は行の色を少し変え、並びは
  終了が近い順。
- **残存価値が残っていたら振替先を聞く**（売却・返金・メルカリ残高など）。ホームの振替と同じ
  シートで `借方 振替先 / 貸方 継続コスト台帳` の**回収の振替**を保存する
  （`metadata.monthlyCostId` + `monthlyCostRecovery: true`）。回収額は割り振る総額から差し引かれ
  （`spreadTotal = 金額 − 回収額`）、月あたりが再計算される。**回収額に上限は無い**: 購入額より
  高く売れたら割り振る総額が負になり、過去にわたって費用減（マイナス表示）になる。
- **勘定科目のアーカイブ = 今日を終了点に記録すること**。資産・負債だけは価値を行方不明に
  しないため、終了点の残高 0 を保存境界と import で fail-closed に確認する。残高があれば
  同区分の科目へ振り替えてから終了する。費用・収入の累計は過去の記録なので、残したまま
  終了できる。
- 費用・収入の分類を連続させたい場合は、同区分の別科目へ累計を 1 対 1 で振り替えてから
  終了する導線も任意で使える。この振替は特別扱いしないため、その日の費目別期間集計には
  旧科目のマイナス・新科目のプラスという大きな組み替えが現れる（支出・収入の総額は不変）。
- 台帳口座に触れる保存仕訳は**購入の仕訳と回収の振替の 2 種類だけ**（どちらも
  `metadata.monthlyCostId` 必須。schema の不変条件）。台帳残高 = 残存価値、という意味を守る。

### 定期ルールとの連携

定期ルール（`RecurringRule`）は `everyMonths`（必須。1 = 毎月）で起票間隔を持つ。
登録 UI は「貸方（支払い元・減る側）→借方（増える・使う側）」の 1 形態だけで、支出・収入・
振替という独自の種別は選ばせない。両辺とも内部集約・残高調整以外の全科目
（`RECURRING_POSTABLE_ROLES`）から選ぶ。**継続コスト台帳を経由して周期分を配分するかは、登録時の
明示トグル**で決める（既定 = 行き先が費用・収入カテゴリなら ON・それ以外は OFF。既定は提案に
すぎず、起票できる科目ならどれでも ON/OFF できる＝クレカ積立のような資産行きも台帳経由を選べる）。
**`role` で動作を決めない = 意味づけはユーザーが決める**。保存表現はトグルそのもので、
`spreadExpenseAccountId` があれば台帳経由（値 = 月割りの計上先。費用に限らない）、無ければ
行き先へ直接起票する。この二形だけが保存形。台帳経由の起票 1 回につき

- 保存される仕訳 `rec-{ruleId}-{month}`: `借方 継続コスト台帳 / 貸方 源泉`（= 購入の仕訳）
- item `ccr-{ruleId}-{month}`: 開始日 = 起票日・終了日 = **次回起票日と同日**（必ず埋まる）

を同一トランザクションで対にする。終了日が次の支払い日と同じなので、毎月ルールは費用が翌起票日に
1 本立ち（1 刻み遅れ）、年払いルールは 12 本の刻みに分かれる。
未来断面ではルール投影が購入の行と費用の行を両方出すので、
台帳が実在しない額まで膨らまない。生成済み item は、その起票時点のルールで内容と配分期間が
確定した事実である。後から周期を短くしたルールが新しい item を作ると、既存 item と配分期間が
重なることがあるが、これは異なる支払いが併存する正常な状態である。同じルール・同じ起票月の
二重生成は、決定的 ID と起票カーソルで防ぐ。

ルール自身も時間軸上の線分として、起票周期とは独立した**存在期間**を持つ。

- `startDate` は存在開始日（含む・必須）、`endDate` は存在終了日（含まない）で、期間は
  **`[startDate, endDate)`**。同じ日に旧ルールを終了し後継ルールを開始しても重ならない。
- `startMonth` は `everyMonths` の周期の位相を決める anchor であり、存在開始日ではない。
  ルールが存在していても、周期上の起票日がまだ来ていなければ仕訳・item は生まれない。
- ルールを止める操作は `endDate` を今日に置く「終了」で表す。もう一度使う場合は、同じ金額・周期・
  位相・フローを引き継ぎ、今日を `startDate` とする独立した新しい線分を作る。これは金額変更の
  分割系譜ではないため、`splitFromRuleId` を持たない。

金額変更では、利用者が次のどちらかを選ぶ。これはルールの存在期間と、継続コスト item を作る
起票日を混同しないための明示的な操作である。

1. **過去から変更**: 同じルールの `amount` を変更し、そのルールが自動生成した全期間の保存仕訳と
   item の金額を同一トランザクションで上書きする。起票後に利用者がその月の金額を手編集していても、
   この操作を選んだ場合は新しいルール金額へ揃える。これは登録金額を最初から訂正するための
   **明示操作**であり、「生成済み item は確定した事実」という原則に対する意図的な例外である。
2. **今日から新しい金額**: 旧ルールの `endDate` と後継ルールの `startDate` をともに今日にする。
   今日以降の起票済み事実があれば後継 segment へ移し、同じ起票を両 segment に残さない。
   今日より前の起票は旧 segment の事実として変えない。移管済み事実も、今回選んだ金額と由来 ID
   だけを新しくし、個別編集済みの摘要・科目・item 名・期間・月割り先は保持する。ルールシートで同時に
   変えた金額以外の設定は次の未起票回から使う。

分割後継は `splitFromRuleId` で直前 segment を指す。同じ連鎖に属するルールの存在期間どうしは
重なってはならず、保存境界と import schema の両方で検証する。境界間の空白、各 segment の
開始点・終了点・周期位相の変更は、この非重複を守る限り許可する。前 segment を物理削除するときは、
残る後継の `splitFromRuleId` を同一トランザクションで外し、dangling 参照を残さない。

「今日から」は旧 segment が今日より前に少なくとも1日存在し、かつ今日も存在期間内にあるときだけ
選べる。開始前・開始当日・終了後のルールには分ける過去がないため、「過去から変更」だけを提示する。

たとえば `4/12` に存在開始し毎月 `20日` 起票するルールを分割する場合、`4/18` の変更では旧 segment
は item を一度も作らず、`4/20` の起票は新 segment に属する。`4/22` の変更では `4/20` の item は
旧 segment に残り、新 segment の最初の起票は翌月になる。

ルールは**定期起票するだけの軽い道具**である（作者決定 2026-08-15）。そこから生まれた
`rec-{ruleId}-{month}` の仕訳と `ccr-{ruleId}-{month}` の item は**読み取り専用**で、個別の編集・
削除・アーカイブ・反対仕訳を一切持たない。金額や周期の調整はルール側の編集（過去から変更 /
今日から新しい金額）と終了・再開だけで行う。この読み取り専用は画面だけでなく保存境界でも
fail-closed に強制する（`upsertEntry` / `deleteEntry` / `upsertMonthlyCost` /
`archiveMonthlyCost` / `deleteMonthlyCost` は対象が rec- / ccr- なら拒否する。ルール自身の内部
処理——遡及の金額変更・分割・catch-up・カスケード削除——はこの保存境界を通らない）。

ルールの物理削除は**カスケード**である。積み木モデル: ルールが下、その起票が上。下を抜けば
上も落ちる。ルール本体・そのルールが起票した仕訳・`ccr-` の item・item に紐づく仕訳（購入の
仕訳と回収の振替）を同一トランザクションで削除する。個別操作を持たない以上、ルールだけを
消して起票を残すと誰も触れない孤児が残るためである。復旧は同じ内容でルールを登録し直せば
よく、確認は起票回数を示す注意文だけにする。

例外は**利用者が自分で作った実仕訳**で、これは最下層の積み木として残る。消える仕訳を指して
いた反対仕訳は残り、`reversalOfEntryId` だけが剥がれる（通常科目どうしの独立した事実になる）。
回収の振替だけは残せない——貸方が継続コスト台帳（内部集約）で、台帳にふれる仕訳は
`monthlyCostId` 必須（不変条件⑧）かつ購入の借方が消えれば台帳残高が負に落ちるため、item と
対で消える（継続コスト item 単体の削除と同じ規則）。

schema v6 は費用ルールを `spreadExpenseAccountId` = 費用科目、
`debitAccountId` = 継続コスト台帳の正規形に限定する。v5 の非正規形はアプリ内で読み替えず、
リポジトリ外の単発変換で直す。v12 は正規形の形はそのままに、`spreadExpenseAccountId` に置ける
配分先を**起票できる全科目**（`RECURRING_POSTABLE_ROLES`）へ広げた（費用・収入カテゴリに
限らない）。金額を変えたときは、上記の「過去から変更」か「今日から新しい金額」を適用する。

### 支出の集計（`src/domain/livingCost.ts`）

- **継続コスト** = 期間内で費用へ割り振られた導出行について、費用科目の借方を加算・
  貸方を減算した純額。
- **通常支出** = 期間内の費用合計 − 継続コスト。補正による費用も通常の支出として含める
  （家計簿はざっくり使い、差分は補正で吸収する。補正の損失は「何かの支出を丸めた余り」なので
  他の支出と同様に扱う）。
- **支出合計** = 通常支出 + 継続コスト（= PL の費用合計）。

購入の仕訳（資産の取得）・返済・振替は費用ではないので含まれない。

## 仕訳一覧は全部出す

仕訳一覧（Journal）は**保存される仕訳と計算で生まれる仕訳を両方**、同じ一覧に日付降順で出す
（ソースは `reportEntriesForAsOf`。分ける必要がない）。計算で生まれた行はタップで元の item /
ルールの編集シートへ飛ぶ。**export / import / スナップショットには計算で生まれる仕訳を混ぜない**
（`exportImport.ts` は `ledger.journalEntries` を直接読む）。
科目で絞り込んだときだけ、その科目の自然な残高方向に対して増える行を緑、減る行を赤で示す。
表示金額には符号を付けず、アクセシブル名で「残高が増える / 減る」も伝える。

## 過去編集モデル（あとから意味を組み替える）

simple-ledger は**監査証跡を固定する帳簿ではなく、生活上の意味をあとから組み替えられる台帳**。
過去の入力や継続コスト資産の定義（金額・終了日・費用の行き先）を後から編集すると、過去の収支・
支出推移・BS・残存価値が再計算される。これは不具合ではなく仕様（UI は「過去から再計算されます」
の注意を出す）。ぐちゃぐちゃにならない現実アンカーが**残高補正**（下記）。締め処理ではなく、
任意の日付で実残高と理論残高をピン留めする。

## 残高補正（「締め」なし・現実アンカー）

実残高との差分を任意の日に補正する（`src/domain/adjustment.ts`、`metadata.adjustment`）。
**月次/年次の「締め」やロックは作らない**。残高補正は「ある日付の実残高に台帳をピン留めする
現実アンカー」であり、**後から編集・削除できる**。

- 差額 → `残高調整費` / `残高調整収入`（`system-adjustment`。初回利用時に自動作成・再利用）。
- 理論残高 = その日付までの仕訳から導出した残高。`delta = 実残高 − 理論残高`。`delta=0` は仕訳を
  作らない。
- 仕訳の向き（2 行のみ）は**借方正規（資産・費用）/ 貸方正規（負債・収入）**の 2 分岐へ一般化した
  （`isDebitNormal` が正本・type ごとの 4 分岐は持たない）。正規方向に増えた = `借方 対象 /
  貸方 調整収入`、減った = `借方 調整費 / 貸方 対象`。asset 増 = `借方 資産 / 貸方 調整収入`・
  asset 減 = `借方 調整費 / 貸方 資産`・liability はその逆、という従来の向きは変わらない。
- **補正は支出/収入に含める**（上記の支出集計を参照。「補正を除外する」設計は誤り）。
- **後編集・削除**（`updateAdjustment` / `deleteAdjustment`）: 編集時の理論残高は**その補正自身を
  除いて**計算し直す（除外しないと補正が二重に効く）。再計算後 `delta=0` になった補正は削除する。
  補正仕訳は Journal では読み取り専用（専用画面でだけ編集・削除）。
- 対象は **`asset` / `liability` / `expense` / `revenue` の全科目**（v12。費用・収入も「その日
  までの実際の累計額」へピン留めできる）。`equity`（初期残高は opening の編集で直す）・内部集約
  ロール（継続コスト台帳を補正で直接動かすと残存価値の導出と矛盾する）・残高調整科目自身
  （補正の相手側）は対象外（`ADJUSTABLE_ACCOUNT_ROLES` が正本）。

## 資金繰りと「自由に動かせるお金」

- **役割分担（作者と合意した設計正本）**: ホーム = 単発の記録 / 毎月のもの = 続くもののルール
  置き場（実際に金が動く → 自動起票・持ち物の消費 → 導出で月割り・過去に波及）/ 資金繰り =
  負債の返済 + 未来を眺める。
- **資金繰りの原資は「自由に動かせるお金」1 値**: `daily-asset` かつ `movable !== false` の
  残高合計（単一正本 = `isFreeAsset` / `freeAssetTotal`・`src/domain/cashflow.ts`）。有限の終了点を
  持つ科目も、終了までの残高と終了時の資金移動を投影するため候補に残す。
  総資金/自由資金という 2 段の概念は持たない。負債返済の投影原資もこれ。
  貸借対照表・資産の内訳は従来どおり全資産を出す（資金繰りだけ絞る）。
- **返済は金額・回数が最初から確定しているので、ルールではなく未来日付の保存される仕訳 N 本**
  （`buildRepaymentEntries` / `createRepaymentEntries`。完済でぴったり終了）。複雑さ（遡及・
  動的再配分）は償却側だけに閉じ込める非対称が肝。返済仕訳には `monthlyCostId` を付けない
  （item 削除で消えると負債残高が狂うため。負債で買った item は削除不可・アーカイブのみ）。
  資金繰りの負債行を展開すると登録済みの返済（未来日付の保存される仕訳）が並び、タップで
  そのまま編集できる（紐づけは「借方 = その負債・未来日付」で引く。metadata は増やさない）。

## ホーム→資産の内訳は 4 枠

**預金など（自由に動かせる現預金）→ 自由に動かせないやつ → 投資 → 継続コスト台帳**の順に
枠で分け、各枠の合計 + 全体合計を出す。継続コスト台帳は 1 行（残存価値の合計・タップで
「毎月のもの」へ＝内訳は台帳画面で見る）。投資を科目で分けたければ（NISA / iDeCo）科目を
増やせば分かれる — 専用機能は作らない。

負債の内訳も同じ構造で、**カード・未払（payment-liability）→ ローン（other-liability）**
の 2 枠に分け、各枠の小計 + 全体合計を出す。

## 勘定科目の変更ルール（`Account`）

- 名前変更: 同一 `id` の表示名を変える。過去仕訳も新名称で表示。
- 新規追加: 登録日を開始点とする科目として追加。
- 存在期間: 開始点・終了点は編集できるが、仕訳・継続コスト item・定期ルールが
  参照する期間より短くできない。勘定科目一覧はヘッダーの断面日、仕訳入力の候補は仕訳日を
  基準に、その日に存在する科目だけを通常表示する。
- 物理削除: **未使用のみ可**（仕訳から参照中は不可・アーカイブを使う）。継続コスト台帳
  （role `continuing-cost-asset`）は削除不可（fail-closed）。
- 区分(type)変更: **未使用のみ可**（使用中は禁止）。UI で無効化し、`upsertAccount` でも fail-closed。
- アーカイブ: 今日を終了点にする。資産・負債だけ残高 0 が条件（残高があれば同区分へ振替）。
  費用・収入は累計を残したまま直接終了でき、同区分への累計振替は任意。
